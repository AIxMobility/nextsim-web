NextSIM 문서NextSIM Documentation

NextSIM은 KAIST AIxMobility Lab에서 개발한 하이브리드 교통 시뮬레이터입니다. 하나의 네트워크 안에서 링크마다 미시(micro)·중시(meso) 모형을 골라 쓸 수 있어, 분석이 필요한 구간만 차량 단위로 정밀하게 보면서 나머지는 빠르게 돌릴 수 있습니다. 이 문서는 NextSIM 의 구조를 소개하고, 설치와 도구별 사용법은 이어지는 가이드에서 다룹니다. 입력 편집과 시뮬레이션 실행·결과 재생은 브라우저의 NextSIM 화면(/nextsim/) 한 곳에서 합니다 — 실행·결과 재생을 맡는 Run 모드와 입력 편집을 맡는 Edit 모드를 상단바에서 오가며 씁니다.

NextSIM is a hybrid traffic simulator from the KAIST AIxMobility Lab. Within one network each link can run under a microscopic or mesoscopic model, so you can study the stretch you care about vehicle by vehicle while the rest runs cheaply. This page explains how NextSIM fits together; installation and the tool guides follow on from it. Editing the inputs and running and replaying simulations all happen on one browser page, NextSIM (/nextsim/), with two modes you switch between in the top bar: Run mode for running simulations and replaying results, and Edit mode for editing the inputs.

NextSIM이란What NextSIM is

NextSIM은 C++17로 작성된 교통 시뮬레이션 엔진과, 그 입력을 만들고 결과를 보는 브라우저 도구로 이루어져 있습니다. 도로망·수요·신호를 XML/JSON으로 정의하면 엔진이 차량의 움직임을 계산해 SQLite 결과 DB로 남기고, 브라우저에서 그 결과를 지도 위에 재생합니다.

NextSIM is a C++17 traffic simulation engine plus browser tooling to author its inputs and inspect its output. You describe the road network, demand, and signals in XML/JSON; the engine computes vehicle movement and writes it to a SQLite result database; the browser replays it on the map.

  • 하이브리드 해상도 — 링크별·시간대별로 micro/meso를 지정합니다.
  • 대중교통 통합 — 버스·TRT·트램·철도 노선과 승객 수요를 함께 시뮬레이션합니다.
  • 신호 제어 — 현시·플랜·시간대(TOD) 기반 신호와 실시간 제어 연동.
  • 검지기 — E1(단면)·E2(구간)·E3(영역) 가상 검지기로 관측값을 수집합니다.
  • 외부 제어 (NextCI) — TCP로 스텝 단위 제어·상태 조회·체크포인트가 가능해 강화학습이나 공동 시뮬레이션에 붙일 수 있습니다.
  • Hybrid resolution — micro/meso is chosen per link and per time period.
  • Transit built in — bus, TRT, tram, and rail lines with passenger demand.
  • Signal control — phases, plans, and time-of-day schedules, with a hook for real-time control.
  • Detectors — virtual E1 (point), E2 (section), and E3 (area) detectors collect observations.
  • External control (NextCI) — step the simulation, query state, and checkpoint over TCP, for reinforcement learning or co-simulation.

하이브리드 시뮬레이션Hybrid simulation

두 모형은 상태를 표현하는 방식과 갱신 주기가 다릅니다. 어느 링크를 어느 모형으로 돌릴지는 mode.xml 이 기간별로 정합니다 (Edit 모드의 Mode 워크스페이스).

The two models differ in how they represent state and how often they update. Which link runs under which model is set per period in mode.xml (the Mode workspace in Edit mode).

Micro (미시)Meso (중시)
상태차량 개별 위치·속도·가속도, 차로 단위링크를 셀로 나눠 셀별 대수
거동차량추종·차로변경 모형 (상태 기계)셀 간 유입·유출 흐름 + 확률적 차로변경
갱신 주기0.1초 (교차로 내부는 1.0초)5.0초
얻는 것차량별 궤적, 차로 수준 상세링크 단위 집계 동태, 낮은 계산 비용
MicroMeso
StatePer-vehicle position, speed, acceleration, on discrete lanesLink split into cells; vehicle counts per cell
BehaviourCar-following and lane-change models (a mode machine)Inter-cell flow plus probabilistic lane change
Update rate0.1 s (1.0 s inside intersections)5.0 s
What you getVehicle trajectories and lane-level detailAggregate link dynamics, cheaply

전역 틱은 0.1초이고 meso 링크는 50틱마다 갱신됩니다 — 즉 micro 는 meso 보다 50배 자주 계산합니다. 경계에서는 차량 표현이 자동 변환되므로, 관심 구간만 micro 로 두고 나머지를 meso 로 두는 것이 일반적인 사용법입니다. meso 모형의 자유속도·후방파속도·용량 값은 네트워크 폴더의 parameter_xml/param.xml 에서 옵니다.

The global tick is 0.1 s and meso links update every 50th tick — micro is computed 50× more often. Vehicles convert between representations at the boundary automatically, so the usual pattern is micro for the area under study and meso everywhere else. The meso model's free-flow speed, backward wave speed, and capacity come from the network folder's parameter_xml/param.xml.

입력 데이터 모델Input data model

엔진은 실행 인자로 경로를 받지 않습니다. 대신 SimulationInput/config.txt 한 줄이 어느 네트워크를 돌릴지를 정합니다.

The binaries take no path arguments. Instead, one line in SimulationInput/config.txt decides which network runs.

network=bucheon

이 값이 곧 경로가 됩니다. 네트워크 하나가 폴더 하나이고, 파라미터도 그 안에 둡니다:

That value becomes the path directly. One network is one folder, parameters included:

SimulationInput/networks/<network>/                  # 네트워크 입력
SimulationInput/networks/<network>/parameter_xml/    # 이 네트워크의 파라미터
SimulationInput/networks/<network>/                  # network inputs
SimulationInput/networks/<network>/parameter_xml/    # this network's parameters

네트워크 폴더에 parameter_xml/ 이 없으면 SimulationInput/parameter_xml/ 을 공용 기본값으로 씁니다. NextSIM 에서 새 네트워크를 만들거나 parameter_xml/ 이 없는 네트워크 패키지를 가져오면 기본 parameter_xml/ 이 함께 복사됩니다. NextSIM 에서 시뮬레이션을 실행하면(Run Selected Network) config.txt 가 그 네트워크로 갱신되므로 직접 편집할 일은 거의 없습니다. 예전 구조(datasets/<branch>/network_xml_<이름>/)의 네트워크 폴더는 서버가 시작할 때 networks/<이름>/ 으로 자동으로 옮기고, 무엇을 옮겼는지 networks/MIGRATION.txt 에 남깁니다.

If a network folder has no parameter_xml/, SimulationInput/parameter_xml/ is used as the shared default. A network created in NextSIM, or imported from a network package that has no parameter_xml/, gets a default parameter_xml/ copied in. Running a simulation from NextSIM (Run Selected Network) rewrites config.txt for that network, so you rarely touch it. Network folders in the old layout (datasets/<branch>/network_xml_<name>/) are moved to networks/<name>/ when the server starts; the moves are listed in networks/MIGRATION.txt.

config.txt 는 시작할 때 한 번만 읽힙니다. 실행 중에 바꿔도 그 실행에는 반영되지 않습니다.
config.txt is read once at startup. Changing it mid-run has no effect on that run.

실행 파이프라인Execution pipeline

config.txt→RouteGenerator→PaxRouteGenerator→UnitTestsSimulation→DB load
  1. config.txt 갱신 — 고른 네트워크를 씁니다. 바이너리에 경로를 넘기는 방법은 이것뿐입니다.
  2. RouteGenerator (기본 켜짐) — Route.json 등 경로 파일을 만듭니다. 입력을 바꾸지 않았다면 꺼서 시간을 아낄 수 있습니다.
  3. PaxRouteGenerator (기본 꺼짐) — 대중교통 승객 경로. PTRoute.json 을 쓰므로 앞 단계 뒤에 옵니다.
  4. UnitTestsSimulation — 시뮬레이션 본체. 진행률은 표준 출력의 사이클 수로 표시됩니다.
  5. DB load — 위 단계와 동시에 돌면서, 엔진이 마무리한 결과 조각을 재생용으로 색인합니다. 그래서 시뮬레이션이 끝나면 곧바로 재생할 수 있습니다.
  1. Write config.txt with the chosen network — this is the only way a path reaches the binaries.
  2. RouteGenerator (on by default) — produces Route.json and friends. Turn it off to save time when the inputs have not changed.
  3. PaxRouteGenerator (off by default) — transit passenger routes; it consumes PTRoute.json, so it follows the previous step.
  4. UnitTestsSimulation — the simulation itself. Progress comes from the cycle count on its standard output.
  5. DB load — runs concurrently with the step above, indexing each result chunk as the engine finalizes it, so replay is ready almost as soon as the run ends.

한 번에 하나의 실행만 진행되며, 실행 이력은 서버에 남아 페이지를 새로 열어도 확인할 수 있습니다.

Only one run proceeds at a time, and the job history is persisted on the server so it survives reopening the page.

이전 실행 결과가 사라졌습니다My previous result disappeared

실행이 끝까지 돌면 그 결과가 SimulationOutput/ 의 이전 결과를 대신합니다. 의도된 동작이니, 남겨야 하는 결과는 실행 전에 복사해 두세요. 취소하거나 실패한 실행은 이전 결과를 되돌려 둡니다 — Run 모드의 Simulation › Load last result 로 다시 열 수 있습니다.

A run that finishes replaces the previous result in SimulationOutput/. That is by design — copy anything you need to keep before starting a new run. A cancelled or failed run puts the previous result back; open it again from Simulation › Load last result in Run mode.

시뮬레이션에 차량이 하나도 안 나옵니다The simulation produces no vehicles

시나리오의 odMatrixID 가 실제로 수요가 들어 있는 매트릭스를 가리키는지 먼저 확인하세요 — OD 매트릭스가 여러 개일 때 가장 흔한 원인입니다. 그리고 기·종점 쌍에 경로가 있어야 하므로 RouteGenerator 를 한 번은 돌려야 합니다.

First check that the scenario's odMatrixID points at a matrix that actually contains demand — the most common cause when a file holds several. Also, each OD pair needs a route, so RouteGenerator has to have run at least once.
